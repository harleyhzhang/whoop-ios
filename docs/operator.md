# Operator runbook

Shipping, backup, and retention for an existing installation that holds real
data. New users should start with [setup](setup.md). The full verification
tiers live in the [migration runbook](whoop-data-migration.md#10-build-sign-install-and-preserve-migration-backups).

Set `WHOOP_DATA_ROOT` to your private data directory before running these tools.

The optional cloud replica runs while the app is active. Initial preparation
still needs enough uninterrupted foreground time to copy and describe the
whole database. Once prepared, one protected local snapshot and authenticated
checkpoint survive backgrounding, network failure, and relaunch; later visits
resume missing chunks instead of repeating preparation. This retains roughly
one database's worth of extra disk space until commit. A changed encryption key,
destination, schema version, or invalid snapshot discards the checkpoint and rebuilds it.
Successful commit removes it. Backup freshness uses the snapshot's original
time, so completing an old upload does not masquerade as current coverage.
Strap collection and sleep publication do not depend on cloud backup.

`sleep-diagnostics.json` is generated by a separate read-only connection and
never performs metric derivation. The same pass writes
`memory-export/daily-YYYY-MM.json`: month chunks of `daily_health_metric`
for the Mac's read-only memory pull, which copies only chunks whose size or
date changed instead of the multi-gigabyte database (Wi-Fi copies of the full
file stall). Only months with rows from the last 40 days, or with no file yet,
are re-read; unchanged chunks are not rewritten.

## Progressive chunk backup

Every rowid table is also backed up progressively to `backup/` beside the
database: one `<table>/<chunk>.sqlite3` per 65,536-row rowid range plus
`manifest.json`. Triggers bump a per-chunk version on every insert, update and
delete, so each pass (after the diagnostics report, 15-second budget, newest
chunks first) rewrites only chunks that changed and never rescans or rehashes
history. The first backfill trickles over several passes; `pending` in the
manifest counts what is left. On the Mac,
`Tools/phone_chunk_backup.py pull --device <id>` copies only changed chunks
over Wi-Fi and `restore <out.sqlite3>` rebuilds a database with per-table row
checks. Migrations that rebuild a table drop its triggers; the next launch
re-adds them and marks that table's chunks changed from its maximum rowid
(no row scan). Its raw-packet census field is omitted;
`historicalSampleTotal` comes from transactional revision counts. For a full
storage census use the storage audit tools. `lifecycle-events.json` retains the
last 128 foreground/background, Bluetooth, and sleep-publication events locally
for investigating unattended gaps; it is not an OS termination log.

## Routine update cost

Routine runtime and presentation updates with unchanged storage/identity use
in-place installation. They validate the existing off-phone checkpoint's small
manifest and file existence, then verify the installed build, running process
and database/WAL advancement. They do not copy or hash the full history, run a
whole-database census, or reject an otherwise valid checkpoint just for its age.
The checkpoint retains its original verification date; new observations remain
on the phone until the next separate backup. This is not a fresh full backup.

Persistence rewrites, restores, backfills, schema and identity changes retain
the heavier tiers. Explicit `--backup-policy full-offphone` also requests the
heavy tier. Full storage reports are forced by the protected/migration install
path and backfills; routine launch reuses a healthy attestation for the same
schema without relabelling it as a new code-revision attestation. Restores
remove the cached report before validation. Routine append/read work must use
indexed recent ranges, bounded batches or transactional counters rather than
scans proportional to lifetime history.

## Physical-phone shipping

From a clean worktree at the exact merged `origin/main` commit, run:

```bash
Tools/ship_phone.sh --commit "$(git rev-parse HEAD)"
```

This is the canonical build, signing, backup, in-place install, launch, and
verification path over Wi-Fi or USB, including migration installs. Keep the
paired phone reachable and unlocked; the verification tier controls backup and
integrity checks, not the connection transport.
`Tools/ship_phone.sh --plan --commit <merged-sha>` reports
the pending commit count and verification tier without requiring the phone, so
routine merges can ship as one intentional checkpoint. `Tools/doctor.sh --mode
migration` performs the strictest read-only preflight.
If shipping returns `needs-unlock` or `needs-verification`, run only the exact
`--resume` command it prints; never uninstall the app. See the
[migration runbook](whoop-data-migration.md#10-build-sign-install-and-preserve-migration-backups)
for the fail-closed verification tiers.

An explicitly selected migration alternative is:

```bash
Tools/ship_phone.sh --commit <merged-sha> --backup-policy on-device-migration
```

This avoids both whole-database wireless transfers and collector suspension.
The app already creates and validates a full, consistent SQLite rollback **on
this phone before migration**. The option requires a recent validated existing
off-phone backup, enough phone space, a known installed build, no preexisting
rollback for this target upgrade, a completed calibration journal exported
before/after with exact matching bytes, and a fresh commit/schema/official-archive
health receipt attesting the new local rollback and retained table counts.
Failure to obtain that receipt leaves a resumable installation; it never
uninstalls. Policy is bound into the manifest and printed resume command.

**Protection differs:** the most recent observations are backed up only on the
phone until a later external/replica refresh. Device loss or storage failure can
lose those newer observations. This is not a fresh off-phone snapshot or an
exact row-by-row host comparison. Choose it only with the operator's explicit
acceptance of that coverage difference. Protected/migration default
`full-offphone` retains the full-copy preservation path. The old off-phone checkpoint is retained
and its coverage time is not advanced by the local-only route. Physical USB is
optional; both modes support wireless.

For a full snapshot, the workflow restarts an existing collector without foreground activation in
Apple's start-stopped state before app code runs. This avoids pausing pending
scene callbacks, whose watchdog could restart a writer during copying.
An LLDB attachment holds that development-signed process stopped for the whole
snapshot, then detaches. A launch pause alone can end during a long transfer.
Failure to confirm the exact stopped process or successful detach rejects the
snapshot; the existing collector resume/relaunch cleanup still runs. No
debugger remains attached for installation or runtime health checks.
Snapshot length/metadata stability, integrity, and exact preserved-row
checks remain mandatory, and the collector is resumed or relaunched afterward.

Device builds reuse `~/Library/Caches/whoop-ios/device-derived-data`. Verified
snapshots retain one standalone database plus required sidecars; automatic
manifest-driven retention keeps current rollback points, two newest snapshots,
and one snapshot per schema and recent month. Retired data stays recoverable for seven
days before a later successful shipping or maintenance run purges it. Run
`Tools/maintain_device_backups.sh` for a dry-run inventory or add `--apply
--adopt-legacy` to validate and compact old snapshots before retirement.
`--retire-unusable` may be added to quarantine only legacy directories that
failed that explicit adoption. This tool never manages canonical WHOOP
source/archive directories. `--apply --purge-now` permanently removes only
already-recorded quarantine entries and is reserved for an explicitly reviewed
cleanup after the retained restore points are revalidated.

Restore points created before the shipping pipeline live in the separate legacy
`app-backups` tree and require a cross-snapshot pass rather than per-directory
deletion. Run `Tools/consolidate_legacy_backups.sh` first as a dry run. With
`--apply`, it selects the fullest integrity-clean database for every schema not
already represented by a managed backup, creates a standalone normalized image,
checks exact preserved-table counts and hashes, and only then quarantines the
redundant folders. `--retire-unusable` includes malformed or empty legacy
folders after schema coverage succeeds; `--purge-now` removes only recorded
quarantine entries. Re-run `Tools/maintain_device_backups.sh` and review a clean
`invalid=0` inventory before an immediate purge.

## Retained movement evidence

Experimental recording controls have been retired; no further calibration
session is required. The local Strain estimate is cardiovascular only, with
actual official scores preferred. See [movement-calibration.md](movement-calibration.md)
for retained evidence, read-only export and OFF-only cleanup of any interrupted
legacy session. Canonical backups still include `motion-calibration.json`;
an existing archive requires a postinstall snapshot and preservation checks.

## Collection freshness and history recovery

A live heart-rate value or connected Bluetooth badge does not prove that the
historical samples used for sleep and recovery are advancing. Check the latest
sensor timestamp in the small `sleep-diagnostics.json` report separately from
its report-generation time. A newly generated report can describe old data.

For a previously bonded device, the app schedules a local system notification
one hour after its last monitored fresh, persisted historical sample (or one
hour after first enabling the monitor if no anchor exists yet). New recent
samples replace that deadline at most every five minutes; replayed history,
future timestamps, live-only heart-rate packets and battery traffic cannot
postpone it. The persisted anchor survives relaunch. Notification delivery
still depends on iOS authorization, Focus and system delivery behavior; this
is an interruption warning, not a guarantee of continuous collection.

The existing historical watchdog first retries a stalled offload. A second
stall without newer durable history reconnects the Bluetooth command channel,
unless persistence is backpressured. It retains raw evidence and never
acknowledges uncommitted history or relaxes sleep-completion gates. Returning
to the foreground also resumes a missing/disconnected link before requesting
history. None of this can reconstruct samples the band never recorded.

Factory-reset RTC recovery is separate from Bluetooth reconnects: some firmware
continues live HR and completes empty offloads while refusing to save samples
to flash with an invalid date. A CRC-valid, request-correlated GET_CLOCK(147)
reply from the current connection can identify a pre-2020 clock. It never
becomes a time reference. With a plausible phone date, the next keepalive sends
WHOOP 5 SET_CLOCK(146), revision 1, little-endian u32 UTC seconds and u16
1/32768-second ticks. Readback must agree within two seconds before recovery is
reported; a BLE write acknowledgement alone is insufficient. Initialization is
limited to three attempts per hour, at least one minute apart, including across
reconnects. Ordinary drift and a future-dated clock do not authorize this repair.
After verified initialization, history retries every 90 seconds until a recent
durable sample arrives. Raw stored timestamps and completion gates stay intact.
Bounded lifecycle events distinguish initialization requested from readback
verified. Reference wire contract: [WHOOP 5 clock commands](https://docs.rs/poop/latest/poop/protocol/enum.Command.html#variant.SetClock).
